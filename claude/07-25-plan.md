# Plan: features on the BallisticCalculator 1.1.11 Tools namespace

Written **2026-07-25**; F4 added **2026-07-26**. This is the design; see the Progress line below for what is
built.

## Context

The 1.1.11 package ships a `BallisticCalculator.Tools` namespace we haven't surfaced yet. Add features on top
of it: a moving-target aim helper on the reticle, and calculators under the **Tools** menu (Approximate DRG
table, Hit probability, BC converter). Each maps to a specific Tools API (verified against the source); we wrap
the API, add UI, and unit-test the wrappers.

**Progress:** F1 moving target ✅ done (2026-07-25) · F2 approximate DRG table ✅ done (2026-07-26, see
[`07-26-drg-plan.md`](Archive/07-26-drg-plan.md)) · F3 hit probability — pending · F4 BC converter ✅ done (2026-07-27).

## Shared infrastructure (build first)

- **Tools menu** — ✅ exists (`Desktop/BallisticCalculator/Views/MainWindow.axaml`, between `_View` and
  `_Windows`). Handlers are wired in `SetupMenuHandlers()`; enable state in `UpdateMenus()`. Hit Probability
  will need an active `ITrajectoryChildWindow` (`_activeChild`); the DRG tools and the BC converter are
  standalone → always enabled.
- **Dialog pattern** — new `Window` subclasses under `Views/Dialogs/`, mirroring `ShotParametersDialog`:
  ctor takes what it needs, `public T? Result`, `OnOK`→`Close(true)` / `OnCancel`→`Close(false)`, shown
  via `await dlg.ShowDialog<bool?>(this)`. Use `MeasurementControl` in `100,*` grids for inputs.
- **Repeated-row input** — superseded by what F2 actually built: a read-only two-column `DataGrid` plus an
  entry row and Add / Change / Delete / Sort buttons (see `DrgFromBcPanel`). Prefer that over the
  `MultiWindPanel` add/remove-row pattern for tabular numeric data.
- **Editor placement** — put the editor in a **panel** in `Common/BallisticCalculator.Panels` with a thin
  `Window` shell in the desktop app: panels are testable headless in `Panels.Tests`, and no dialog under
  `Views/Dialogs/` has test cover. The panel raises `CloseRequested` (and similar) rather than owning windows.
- **.drg save flow** (net-new; none exists) — mirror `AmmoLibraryRecordPanel`'s
  `FileDialogService.SaveFileAsync` usage (`DefaultExtension="drg"`, filter `drg`) and call
  `DrgDragTable.Save(path)` (see the `ballistic-calculator` skill / `references/custom-drag.md`).

## Feature 1 — Moving target (reticle aim overlay) — ✅ DONE (2026-07-25)

**Status:** Implemented. `ReticlePanel` has a "Moving target" section (enable + azimuth-style direction
dial synced with a numeric degrees input + speed in mi/h·km/h), reusing the Target distance. A dashed
"aim here" box is drawn via `ReticleCanvasControl.MovingTargetBox`, offset by
`ReticleOverlayController.CreateMovingTargetOverlay` (hold-off = −windage − lead). Target angular size and
the lead hold-off are shown in the current angular unit. Also added a center-aimed dead zone and target
size to the summary along the way.

**Goal:** user enters target motion direction (relative to line of sight) + speed; show a dotted target
outline on the reticle at the aim-off point.

**API:** `Tools.MovingTargetLead.LeadAngle(Measurement<VelocityUnit> speed, Measurement<AngularUnit>
direction, TrajectoryPoint point)` → angular lead. Direction convention = wind (0° = along LoS/no lead,
90° = full crossing from right, positive = left). Only the crossing component leads (horizontal).

**Where:** shared reticle stack (Common). Add inputs to `ReticlePanel` (near the existing Target inputs):
a "Moving target" enable + Direction (`MeasurementControl<AngularUnit>`, degrees) + Speed
(`MeasurementControl<VelocityUnit>`). Reuse `TrajectoryToReticleCalculator.FindDistance` to get the
`TrajectoryPoint` at the target distance and `ReticleOverlayController.CalculateAngularSize` for the box
size (same as `CreateTargetOverlay`).

**Overlay math:** new `ReticleOverlayController.CreateMovingTargetOverlay(...)` — like `CreateTargetOverlay`
but shift the box center horizontally by the computed `LeadAngle` (X += lead, sign per windage
convention): "aim here" box. Returns a rectangle (or ellipse) at `(impactWindage − leadX ± w/2,
impactDrop ± h/2)`.

**Dotted rendering:** the reticle element model (`ReticleRectangle`, etc.) and `SkiaReticleCanvas` are
NuGet types with **no dash support**, and dashing can't be signaled per element. Recommended: give
`ReticleCanvasControl` a dedicated `MovingTargetBox` property (angular center + size) that its
`CustomDrawOp` draws directly with a dashed `SKPaint` (`SKPathEffect.CreateDash`), using the existing
`AngularToPixel` mapping — bypasses the element pipeline and keeps the dotting self-contained.
*(Alternative if we want to avoid touching the canvas: approximate the outline with many short
`ReticleLine`/`ReticleCircle` segments in an overlay collection.)*

**Files:** `ReticlePanel.axaml(.cs)`, `Controllers/ReticleOverlayController.cs`,
`Controls/ReticleCanvasControl.axaml.cs` (+ `Canvas/SkiaReticleCanvas.cs` if extending paint).
**Tests:** `ReticleOverlayController` — lead box offset direction/magnitude for a known point; 0°
direction → no lead (box == impact box). Reuse the trajectory scenario builder from existing tests.
**Decision:** extend the Target inputs vs a separate "Moving Target" radio mode (recommend a separate mode).

## Feature 2 — Approximate DRG table (two Tools dialogs) — ✅ DONE (2026-07-26)

**Status:** Implemented and pushed. Designed and recorded in detail in
[`07-26-drg-plan.md`](Archive/07-26-drg-plan.md) — read that rather than this section, which is the original sketch.
Delivered as two panels (`DrgFromBcPanel`, `DrgFromVelocitiesPanel`) with scrollable shells under
**Tools → Approximate Drag Table**, all-or-nothing CSV import with units required in the file, and full
`.drg` header metadata. Notable departures from the sketch below: rows are edited in a two-column `DataGrid`
with an entry row (not repeated `MeasurementControl` rows), BC knots are always keyed by Mach and carry their
own drag table, and the library's multi-BC scale bug was found and fixed upstream in **1.1.11.3** (weight and
diameter are now inputs to `Build`, not metadata).

Both produce a `DrgDragTable` and save it as `.drg`.

**2a. From BCs** — `DrgDragTableFactory.Build(AmmunitionLibraryEntry ammunition, DragTableId baseTable,
IEnumerable<BcAtMach> bcCurve)`. `new BcAtMach(double mach, double bc)`. Synthesizes
`Cd_custom(M) = Cd_base(M)/BC(M)`; run the result with BC value 1.0 + table `GC`.
- Dialog inputs: base table (combo G1/G2/G5/G6/G7/G8/GI/GS/RA4), bullet name/weight/diameter (for the
  `AmmunitionLibraryEntry` metadata), and a repeated-row list of `(Mach, BC)` knots.

**2b. From Velocities** — `Tools.RadarDragTableFactory.Create(IEnumerable<RadarReading> readings,
Measurement<WeightUnit> bulletWeight, Measurement<DistanceUnit> bulletDiameter, Atmosphere atmosphere,
string name)`. `new RadarReading(Measurement<DistanceUnit> distance, Measurement<VelocityUnit> velocity)`.
Recovers Cd from measured downrange velocity decay.
- Dialog inputs: bullet weight/diameter/name, atmosphere (default `new Atmosphere()` or pull from active
  shot if present), and a repeated-row list of `(distance, velocity)` readings.

**Shared:** a thin `Common/BallisticCalculator.Types/DragTableBuilder.cs` wrapping both factory calls
(pure, testable). Dialogs (`Views/Dialogs/ApproximateDrgFromBcsDialog`, `...FromVelocitiesDialog`) collect
rows, call the wrapper, then `SaveFileAsync` + `DrgDragTable.Save`. Prefill bullet weight/diameter from
the active shot's ammunition when a trajectory window is active.
**Tests:** `DragTableBuilder` — Build/Create return a non-null `GC` `DrgDragTable` for representative
inputs; input validation (need ≥2 knots/readings).
**Decisions:** row-input UI (MultiWind-style vs grid); whether to also offer "add to ammo library" vs
save-to-file only.

## Feature 3 — Hit probability (Tools dialog)

**API:** `Tools.HitProbability.Estimate(TrajectoryCalculator calc, Ammunition ammo, Atmosphere atmo,
Rifle rifle, ShotParameters shot, Wind[] wind, HitProbabilityParameters p, DragTable dragTable = null)`
→ `HitProbabilityResult { double HitProbability; int?[] ShotsFor50/75/90/95/98Percent;
IReadOnlyList<ShotImpact> Shots }`. Monte-Carlo over the shooter's error budget; nominal conditions land
dead center (so the shot must be zeroed/come-up correct for the range).

`HitProbabilityParameters` (defaults in parens): `TargetSize` (circular vital-zone diameter), `GroupSize`
(angular, ~4 MOA ordinary / 1 MOA precision), `MuzzleVelocityDeviationPercent`, `DistanceErrorPercent`,
`WindErrorPercent`, `HorizontalPositionMultiplier` (1 supported → prone 2/kneeling 4/standing 5),
`VerticalPositionMultiplier`, `Shots` (1000), `Seed`. `ShotImpact { Horizontal, Vertical }` (+left/+up).

**Where:** Tools menu → `HitProbabilityDialog(MeasurementSystem, ShotData)` (needs active
`ITrajectoryChildWindow`). Build the calc inputs from `ShotData` reusing `ZeroingCalculator.BuildInputs`
(rifle + zeroed shot) and a `ShotParameters` at the chosen **target distance** (MaximumDistance = target
distance, with the zero applied via `shot.Apply(CalculateZeroParameters(...))`) so nominal lands center.
- Dialog inputs: target distance + `HitProbabilityParameters` fields (pre-seeded with the defaults above),
  target size defaulting to the summary's 500 mm / 20 in.
- Output: single-shot hit probability (%), the "shots to hit with 50/75/90/95/98%" table, and a scatter
  plot of `Shots` (`ShotImpact` H/V miss vs target circle).

**Wrapper:** `Common/BallisticCalculator.Types/HitProbabilityCalculator.cs` — takes `ShotData` +
`HitProbabilityParameters` + target distance, assembles the library call, returns the result (pure,
testable with a fixed `Seed`).
**Tests:** `HitProbabilityCalculator` with fixed `Seed` — probability in [0,1]; larger target ⇒ higher
probability; tighter group ⇒ higher probability.
**Decisions:** scatter plot via ScottPlot (already referenced) vs a simple canvas; which target-distance
default (e.g. the shot's max distance).

## Feature 4 — Ballistic coefficient converter (Tools dialog) — ✅ DONE (2026-07-27)

**Status:** Implemented as `BcConversionCalculator` (`Common/BallisticCalculator.Types`), `BcConverterPanel`
(`Common/BallisticCalculator.Panels`) and the `BcConverterDialog` shell, under **Tools → Convert Ballistic
Coefficient…**; 42 new tests. **The layout below was superseded** by the four-field form the user specified:

```
Source BC          [ 0.365   G1 ]
Destination Table  [ G7        ▾ ]
Reference Velocity [ 2700  ft/s ]
Target BC          [ 0.183G7     ]   (read-only, follows the inputs — no Convert button)
                        [ Set Atmosphere ] [ Close ]
```

Departures from the design below, all deliberate:
- **No reference-band table, and no Mach/velocity radio pair** — the reference is a velocity only, and the
  single Target BC field replaces the band. The honesty the band was for is carried instead by a standing note
  ("only exact at its reference velocity"), the reference Mach quoted in the status line, and a red warning
  below Mach 1.5.
- **No Copy button** — the read-only `TextBox` holds the parseable text form (`0.183G7`), so select-and-copy
  already works.
- **Set Atmosphere reuses the velocities editor's `AtmosphereDialog`** (the panel raises `AtmosphereRequested`,
  the shell owns the window). It affects the speed of sound and nothing else, which the status line states.
- Validation messages carry **no `paramName`** — `ArgumentException.Message` would otherwise append
  "(Parameter 'source')" to text shown to the user verbatim. (`DragTableBuilder` still has that wart.)
- Source is seeded from the active window's ammunition, **skipping GC and form-factor coefficients** since
  neither can be converted. Destination defaults to the other half of the question (G7, or G1 for a G7 source).
- **GC is not offered on either side.** `BallisticCoefficientControl` gained
  `AllowCustomTable` (default true, so the ammunition panel keeps GC for a custom `.drg`); with it false the
  control drops GC from the list *and* refuses to hold a GC value, since showing the number under a table it was
  not quoted against is worse than showing nothing. Also applied to the BC-curve knot editor, which already
  refused GC knots on Add. `BcConversionCalculator` keeps its own GC guards — it is a public API.

Convert a published BC from one standard table to another (the everyday G1 ↔ G7 question), using
`Tools.BallisticCoefficientConverter`. Small, self-contained, and no file output — the natural next feature
after the drag-table editors, which already lean on this converter internally.

**API** (verified in the 1.1.11.3 source):
```
Tools.BallisticCoefficientConverter.Convert(BallisticCoefficient source, DragTableId targetTable, double referenceMach)
Tools.BallisticCoefficientConverter.Convert(BallisticCoefficient source, DragTableId targetTable,
    Measurement<VelocityUnit> referenceVelocity, Atmosphere atmosphere = null)   // velocity -> Mach via speed of sound
```
`BC_target = BC_source * Cd_target(M) / Cd_source(M)` at the reference Mach. Throws `ArgumentException` when
the source is a **form factor** rather than a coefficient, or when either side is **GC**; throws
`ArgumentOutOfRangeException` for a non-positive reference.

**The honest part — a converted BC is only exact at its reference.** From the library's own documentation and
confirmed by measurement: ~1% against manufacturer-published pairs at Mach 1.8–2.5 (where the G1/G7 drag ratio
sits near 2.0), degrading to roughly **9% low near Mach 1.3**, where the two reference curves diverge in shape.
The `Cd_G1/Cd_G7` ratio is not monotonic — 2.05 at Mach 0.8, dipping to 1.26 at Mach 1.0, then climbing
1.65 → 1.77 → 1.91 → ~2.0 above Mach 1.8. So the UI must **show the whole band, not just one number**, or it
will quietly imply a precision the conversion does not have.

**Where:** Tools → *Convert Ballistic Coefficient…*, standalone (no trajectory window needed). Panel + thin
shell per the pattern in [`07-26-drg-plan.md`](Archive/07-26-drg-plan.md) §1d — `BcConverterPanel` in
`Common/BallisticCalculator.Panels`, shell `Views/Dialogs/BcConverterDialog`, so it is testable headless.

```
Source BC     [ 0.462 G7 ▾ ]          (BallisticCoefficientControl)
Convert to    [ G1 ▾ ]                (standard tables only, GC excluded, ≠ source)
Reference     ( ) Mach     [ 2.00  ]
              (•) Velocity [ 2700 ft/s ]
┌ Reference        │ Converted BC ┐   (DataGrid: the band, reference row highlighted)
│ Mach 1.20 (1340) │ 0.780G1      │
│ Mach 1.50 (1675) │ 0.883G1      │
│ Mach 2.00 (2233) │ 0.920G1      │
└──────────────────┴──────────────┘
At the reference: 0.920G1.  Below about Mach 1.5 the conversion loses accuracy (~9% near Mach 1.3).
                                          [ Copy ]  [ Close ]
```

- **Reference as Mach or velocity**, one radio pair. Velocity uses the standard atmosphere for the speed of
  sound (state it in a note); a `Set Atmosphere` button is deliberately *not* offered — the reference band is
  about curve shape, and adding air conditions here would suggest more precision than exists.
- **The band table** is the point: rows at Mach 1.0/1.2/1.35/1.5/1.75/2.0/2.25/2.5 with the equivalent velocity
  shown alongside, so the user can see how much the answer moves with the reference. The row nearest the
  chosen reference is marked.
- **Transonic warning** shown whenever the reference is below ~Mach 1.5.
- **Copy** puts the converted BC in the text form the app parses (`0.920G1`) on the clipboard.
- Out of scope for the first cut: writing the result into the active ammunition (the drag-table editors set the
  precedent of not reaching into the open shot), and converting *to* GC (that is what the drag-table editors
  are for).

**Wrapper:** `Common/BallisticCalculator.Types/BcConversionCalculator.cs` — validates (coefficient not form
factor, neither side GC, positive reference, target ≠ source) with user-facing messages, converts, and builds
the band as `(double Mach, Measurement<VelocityUnit> Velocity, BallisticCoefficient Converted)` rows. Pure and
testable; the panel only formats.

**Tests:** `BcConversionCalculator` — G1→G7 and back round-trips exactly at the same reference (a pure ratio);
a known published pair lands within 1% at Mach 2.0; the band is monotonic in the same direction as the
`Cd_G1/Cd_G7` ratio; same-table conversion returns the input unchanged; form factor, GC on either side, and a
non-positive reference all throw with readable text. Panel tests: reference mode toggle keeps the value, the
band marks the right row, the warning appears below Mach 1.5, Copy puts parseable text on the clipboard.

## Tools API reference (verified against BallisticCalculator 1.1.11)

```
Tools.MovingTargetLead.Lead(Measurement<VelocityUnit> speed, Measurement<AngularUnit> dir, TrajectoryPoint pt) -> Measurement<DistanceUnit>
Tools.MovingTargetLead.LeadAngle(Measurement<VelocityUnit> speed, Measurement<AngularUnit> dir, TrajectoryPoint pt) -> Measurement<AngularUnit>
    (also TimeSpan/range overloads)

DrgDragTableFactory.Build(AmmunitionLibraryEntry ammo, DragTableId baseTable, IEnumerable<BcAtMach> curve) -> DrgDragTable
    new BcAtMach(double mach, double bc)
Tools.RadarDragTableFactory.Create(IEnumerable<RadarReading> readings, Measurement<WeightUnit> weight,
    Measurement<DistanceUnit> diameter, Atmosphere atmo = default, string name = null) -> DrgDragTable
    new RadarReading(Measurement<DistanceUnit> distance, Measurement<VelocityUnit> velocity)
Tools.BallisticCoefficientConverter.Convert(BallisticCoefficient src, DragTableId targetTable, double referenceMach)
Tools.BallisticCoefficientConverter.Convert(BallisticCoefficient src, DragTableId targetTable,
    Measurement<VelocityUnit> referenceVelocity, Atmosphere atmosphere = null)
    BC_target = BC_src * Cd_target(M)/Cd_src(M); exact only at that reference.
    Throws for a form factor source, for GC on either side, and for a non-positive reference.

Tools.HitProbability.Estimate(TrajectoryCalculator, Ammunition, Atmosphere, Rifle, ShotParameters,
    Wind[], HitProbabilityParameters, DragTable = null) -> HitProbabilityResult
  HitProbabilityParameters: Measurement<DistanceUnit> TargetSize; Measurement<AngularUnit> GroupSize;
    double MuzzleVelocityDeviationPercent, DistanceErrorPercent, WindErrorPercent,
    HorizontalPositionMultiplier, VerticalPositionMultiplier; int Shots; int? Seed;
  HitProbabilityResult: double HitProbability; int? ShotsFor50/75/90/95/98Percent;
    IReadOnlyList<ShotImpact> Shots;  ShotImpact { Measurement<DistanceUnit> Horizontal, Vertical }  (+left/+up)
```
