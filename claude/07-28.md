## F-1 — A form factor with no bullet diameter throws out of the OK handler

- **Found:** 2026-07-28, writing `docs/ammunition-tab.md`
- **Status:** **fixed** 2026-07-29 — `AmmoPanel.Problems()` requires a diameter (and a positive form
  factor and weight) whenever the form-factor switch is on; `ShotDataPanel.Validate` returns it and the
  dialog shows it. Guarded as well, by `ShotCalculator.TryCalculate`.
- **Area:** the calculation path from `ShotParametersDialog.OnOK` →
  `MainWindow.OpenNewTrajectory` → `ShotCalculator.Calculate` → `ShotTrajectoryCalculator.Calculate`

**Steps to reproduce**

1. `Trajectory → New`, fill the Ammunition tab with weight, BC and muzzle velocity.
2. Tick **BC is Form Factor**. Leave **Diameter** empty.
3. Press OK.

**What happens:** `Ammunition.GetBallisticCoefficient()` throws
`ArgumentException: If form-factor is used, the bullet diameter must be set` — a form factor is turned
into a coefficient through the bullet's sectional density, which needs the diameter.

**Verified** by calling `ShotTrajectoryCalculator.Calculate` with exactly that data in a throwaway test:
the exception is real and comes out of the calculation, not out of validation.

**Why it matters more than it looks:** this is not an exotic combination. **Every `.drg` shot is a
form-factor shot** — `Browse…` sets the BC to `1 GC` and ticks the switch — so any custom drag table
whose header carries no diameter lands here. `Browse…` fills the diameter when the file has one, and
older `.drg` files store that slot as `0`.

**Where it goes wrong architecturally:** nothing on the path catches it. `OpenNewTrajectory` is
`async void`, so the exception surfaces as an unhandled exception on the UI thread rather than as a
message the user can act on. `ShotDataPanel.Validate` checks that fields are *present*, not that the
combination is *computable*.

**Suggested fix:** validate the combination where the other validation lives — if the form-factor switch
is on, require a diameter, and say so in the same style as the existing messages. A `try`/`catch` around
the calculation with the exception text shown would also be an improvement over a crash, but it treats
the symptom.

### F-1b — same class: a GC coefficient whose `.drg` cannot be found — **fixed** 2026-07-29

`ValidateDragTable` throws `ArgumentNullException("The drag table shoudn't be null if the ballistic
coefficient is custom")` when the BC table is `GC` and no table was supplied. That happens when
`CustomDragTableLoader.ResolvePath` cannot find the stored file name — neither as given nor under
`data/drg` and its subfolders. Realistic route: someone opens a shared `.trajectory` or `.ammox` that
references a `.drg` they do not have. Same uncaught path, same `async void`.

**Fix:** `AmmoPanel.Problems()` resolves the stored file name through `CustomDragTableLoader.ResolvePath`
whenever the BC table is `GC`, and names the file it looked for (and where) when it cannot be found.
The `Open` path is guarded too and now reports the failure instead of writing to `Console.Error`, which
nobody sees.

### F-1c — same class: a zero distance the bullet cannot reach — **fixed** 2026-07-29 (BallisticCalculator 1.1.13)

`CalculateZeroParameters` throws `InvalidOperationException("The projectile cannot reach the zero
distance")`. Found while writing `docs/zero-tab.md`; reachable by asking for a zero further out than the
load can carry (a subsonic pistol load zeroed at 1,000).

This one cannot be validated from the panel — whether a load reaches a distance is the calculation's own
answer, not a property of the input — and catching `InvalidOperationException` by type would have swallowed
unrelated faults.

**Fix:** BallisticCalculator 1.1.13 raises `ZeroRangeCantBeReachedException`, so it can be caught by type.
`ShotCalculator.Explain` maps it (and the new `TrajectoryCannotBeCalculatedException`, for numbers the solver
cannot integrate) to a sentence saying what to change; `MainWindow.ReportCalculationFailure` shows those in a
plain `MessageDialog`, and keeps `ExceptionDialog` with its stack trace for anything the engine has *not*
named — a bug dressed up in friendly words is a bug you never hear about. Both new types derive from
`InvalidOperationException`, so they must be caught before any broader handler.

The `TrajectoryCannotBeCalculatedException` half also got validation, since its usual cause is a field that is
present but zero: `AmmoPanel.Problems()` now rejects a non-positive ballistic coefficient, weight or muzzle
velocity by name.

**Taken together**, F-1/1b/1c said the same thing: the calculation raises meaningful exceptions and the
UI had no seam for turning them into messages. That seam now exists (`ShotCalculator.TryCalculate` +
`ExceptionDialog`) — but it is the net, not the fix: a caught exception is still a dead end for the user,
which is why F-1 and F-1b are validated as well.

## F-2 — Nothing catches a calculation failure on the recalculate path either

- **Found:** 2026-07-28
- **Status:** **guarded** 2026-07-29 — all three call sites (`OpenNewTrajectory`, `EditParameters`,
  `Open`) go through `ShotCalculator.TryCalculate` and show `ExceptionDialog` on failure. `EditParameters`
  now recalculates **before** assigning `ShotData`, so a failed edit leaves the visible shot intact
  instead of half-updating it. `DoSave` reports its failures too — a silent failed save is a file the user
  believes they have.
- **Area:** `MainWindow` — `View → Edit Parameters` recalculates through
  `ShotCalculator.Calculate(dialog.Result, …)` with no `try`

The same three exceptions can be raised by editing an existing shot into an uncomputable state, which is
arguably the likelier route: the window already exists, so a crash there loses work the user can see.
`DoSave` and `Open` do wrap their I/O in `try`/`catch` (writing to `Console.Error`), so the pattern
exists in the file — it is the calculation that is unguarded.

## F-3 — `AmmoPanel` does not restate units after a load — **NOT A DEFECT** (closed 2026-07-29)

- **Found:** 2026-07-28, writing `docs/ammunition-tab.md`
- **Status:** **closed, working as intended.** Nikolay's ruling: if the ammunition is stored metric, show
  it metric. A saved load's units are the author's own record of the load, and restating them in the
  window's system would throw that away — the same reasoning as the precision-transparency rule. The
  inconsistent-looking labels are the cost, and they are worth paying.
- **The one exception**, which is *already implemented*: a `.drg` header stores SI values (kg / m) as an
  artefact of the file format, carrying no user intent, so `AmmoPanel.OnBrowseCustomTable` converts weight,
  diameter and length to the panel's current units. Committed in `296793e`; covered by
  `AmmoPanelTests.BrowseCustomTable_ShouldConvertSiValuesToTheCurrentSystem`.
- **Therefore `docs/ammunition-tab.md` stays as written** ("A loaded value keeps the units it was saved
  in") — the note below about that paragraph becoming wrong no longer applies. `units.md` rule 1 needs the
  carve-out spelled out instead.

The original report follows, for the record.
- **Area:** `Common/BallisticCalculator.Panels/Panels/AmmoPanel.axaml.cs` — the `Ammunition` setter

**Steps to reproduce**

1. `Trajectory → New → Imperial`.
2. On the Ammunition tab press **Load** and pick `data/legacy-ammo/7N6.ammo`.
3. Look at the tab: weight in **grams**, muzzle velocity in **m/s**, diameter and length in **mm**,
   everything else on the dialog in imperial.

The shipped library contains both kinds, which is what makes this easy to hit: `7N6.ammo` is stored
metric (`3.4g`, `870m/s`, `5.6mm`), `45acp 230gr FMJ (4in).ammo` imperial (`230gr`, `850ft/s`, `0.451in`).

**Why it happens:** the setter uses `SetValue`, which preserves each value's own unit by design — the
precision-transparency rule in `CLAUDE.md`. That is correct for *precision* and wrong for *presentation*,
and it is precisely the defect that was fixed for `AtmospherePanel` on 2026-07-27 (commit `3c49dbc`),
where the setter now ends with `ApplyMeasurementSystem(convert: true)`.

**Rule it breaks:** [`units.md`](units.md) rule 1 — "a dialog is either imperial or metric, never both.
No field opts out." `units.md` also flags this as the decision to watch.

**Suggested fix:** the `AtmospherePanel` fix, applied here — restate every field in the panel's system at
the end of the setter, converting rather than relabelling. Worth checking the other panels that take a
library object with its own units in the same pass: `ZeroAmmoPanel` (wraps `AmmoPanel`), `RiflePanel`
(sight height and twist from a preset or a file), `WindPanel`, `ParametersPanel`.

**Note for the manual:** `docs/ammunition-tab.md` currently documents the behaviour as it is ("a loaded
value keeps the units it was saved in"), with the shipped files as the example. Fixing this makes one
paragraph there wrong — search for *"A loaded value keeps the units"*.

## F-4 — A ticked but half-filled zero override is silently ignored

- **Found:** 2026-07-28, writing `docs/zero-tab.md`
- **Status:** **fixed** 2026-07-29 — each override answers for itself (`ZeroAmmoPanel.Problems`,
  `ZeroAtmospherePanel.Problems`, `ZeroWindPanel.Problems`), `ZeroPanel.Problems` aggregates them and adds
  the ticked-but-empty impact-offset group, and `ShotDataPanel.Validate` returns the lot. The zero
  ammunition delegates to `AmmoPanel.Problems`, so it names the missing field — and gets the F-1/F-1b
  checks too, which apply to the zero ammunition just as much.
- **Area:** `ZeroAmmoPanel.Ammunition`, `ZeroAtmospherePanel.Atmosphere` (and `ZeroWindPanel.Wind` by the
  same shape), plus `ShotDataPanel.Validate`, which never looks at them

Each override getter returns null when its checkbox is clear — correct — but also when the checkbox is
**ticked and the fields are incomplete**, because it just forwards the inner panel's own null. Null then
means "same as the shot" in `ZeroingCalculator.BuildInputs`
(`ZeroAmmunition = zeroParams.Ammunition ?? ammo`), so:

> Tick **Other ammunition for zero**, fill in a BC and a muzzle velocity but forget the weight, press OK
> — the shot computes, with the zero silently using the *shot's* ammunition. Nothing says so.

This is the same failure mode the dialog is careful about everywhere else: `Validate` reports a
half-filled Weather or Rifle tab as *"Not all required data filled in"*. The zero overrides are outside
that check, and they are the one place where the fallback is plausible enough to go unnoticed — the
numbers move a little, not obviously.

**Suggested fix:** have `ZeroPanel` report "ticked but incomplete" for each group, and add it to
`Validate`'s `incompletePanels` as `Zero`. Cheap, and it closes the last silent path in that dialog.

**Documented meanwhile:** `docs/zero-tab.md` states it as a trap under "Things that catch people out".

## F-5 — Dialled clicks are silently ignored when the sight has no click size

- **Found:** 2026-07-28, writing `docs/parameters-tab.md`
- **Status:** **fixed** 2026-07-29 — `ParametersPanel.Problems()` reports each axis separately, naming the
  Rifle-tab field to fill in. Validation rather than the greyed-spinner approach the note below suggested:
  the click size lives on another tab, so a disabled control with no explanation is the same dead end in a
  different costume, and validation says *why*.
- **Area:** `ParametersPanel.ClicksToAngle` — `if (clicks == 0 || clickSize == null) return null;`

A click count is meaningless without a click size, so returning null is the only correct arithmetic. The
problem is that nothing tells the user: **V-Clicks** and **H-Clicks** accept −200…200, the shot computes,
and the dialled adjustment is simply absent. The click size lives on a *different tab* (Rifle), which is
what makes it easy to have one without the other — and the sight presets that carry no click values
(`EOTech@M4`, `Elcan Specter@M4`, the two .22LR entries) put the user in exactly that state.

**Suggested fix:** disable the two click spinners while the Rifle tab has no click size, with a hint
naming the missing field — the *Twist Rate* box already uses that pattern, staying greyed until a rifling
direction is chosen. Failing that, add it to `Validate` as an incomplete-Parameters case.

**Documented meanwhile:** `docs/parameters-tab.md`, under the dialled-clicks section and again under
"Things that catch people out".

## F-6 — The reticle editor has no unsaved-changes protection anywhere

- **Found:** 2026-07-28, writing `docs/reticle-editor.md`
- **Status:** **fixed** 2026-07-29 — a dirty flag set by every element operation, by the **Set** button and
  by editing any parameter field; `ConfirmDiscardChangesAsync` guards `File → New`, `File → Open` and
  `OnWindowClosing` with a Save / Don't Save / Cancel prompt; the title carries the file name and an
  asterisk. Cleared only by a *successful* save, so a cancelled Save As or a failed write still stops the
  operation rather than losing the work the user asked to keep.
- **One design note.** Telling a load's own control notifications from a real edit is the whole difficulty
  here: filling the parameter controls makes them raise `Changed`, partly synchronously and partly posted
  to the dispatcher. Two attempts at time-based suppression both failed — the second swallowed genuine
  edits made before the dispatcher settled. It compares content instead: `MarkClean` snapshots the fields,
  and a field notification dirties the document only when the fields differ from that snapshot. No timing,
  nothing to get wrong under load.
- **Area:** `Desktop/ReticleEditor/Views/MainWindow.axaml.cs` — `OnFileNew`, `OnFileOpen`,
  `OnWindowClosing`

Nothing in the editor tracks or guards a dirty document:

- **`File → New`** builds a fresh 10 × 10 mil reticle straight over the current one. No prompt.
- **`File → Open`** replaces it likewise.
- **`OnWindowClosing`** saves the *window state* (size, splitter, font) and returns. It never looks at the
  document, so closing the window discards an unsaved reticle silently.

An hour of element-by-element work is a stray `Ctrl+N` away, and the editor is exactly the kind of tool
where that hour is plausible — every element is typed by hand, there is no undo, and the drawing cannot be
recovered from the preview.

**Suggested fix:** a dirty flag set by `CommitReticleParameters` and by each element operation, checked by
New, Open and `OnWindowClosing` (which can cancel via `WindowClosingEventArgs.Cancel`). A three-button
Save / Discard / Cancel prompt is the conventional shape; even a bare confirmation would remove the
data-loss path.

**Documented meanwhile:** `docs/reticle-editor.md` says plainly that nothing warns you and to use
*Save As* before an experiment. That paragraph should go when this is fixed.

## N-1 — Modal dialogs are hidden by their owner under WSLg — **not our bug**

- **Found:** 2026-07-29, testing the unsaved-changes prompt
- **Status:** closed. A **WSLg** artifact, and not Avalonia's either: a native Tk program reproduces it
  exactly there, and the same build is correct on real Ubuntu 24.04 and on Windows. Two workarounds were
  tried and both reverted — one did nothing, the other made WSLg render dialogs empty.
- **Written up in full** in [`wslg-modal-dialogs.md`](wslg-modal-dialogs.md) — symptom, the test that proves
  it is stacking rather than hiding, the native repro, both failed workarounds and what to do if it ever
  appears on a real desktop. User-facing version: [`docs/known-problems.md`](../docs/known-problems.md).

## What the 2026-07-29 pass added, in one place

  message, and the full chain with stack traces in a read-only monospace box, plus **Copy**.

  list instead of clipping at a fixed 150 px.
