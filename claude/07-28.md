# Findings — 2026-07-28

Turned up while writing the user manual (`docs/`), by reading the panel and engine code rather than by
manual testing. None is fixed. Numbered F-n here rather than D-n because
[`DEFECTS.md`](DEFECTS.md) currently holds only closed entries; if these get filed there they become
D-003 onwards.

Verified as noted. **F-1 was reproduced by running the calculation**; F-2 was read from the code path;
F-3 was reproduced by inspecting the shipped data files against the panel's load behaviour.

## F-1 — A form factor with no bullet diameter throws out of the OK handler

- **Found:** 2026-07-28, writing `docs/ammunition-tab.md`
- **Status:** open
- **Area:** the calculation path from `ShotParametersDialog.OnOK` →
  `MainWindow.OpenNewTrajectory` → `ShotCalculator.Calculate` → `ShotTrajectoryCalculator.Calculate`

**Steps to reproduce**

1. `Trajectory → New`, fill the Ammunition tab with weight, BC and muzzle velocity.
2. Tick **BC is Form Factor**. Leave **Diameter** empty.
3. Press OK.

**What happens:** `Ammunition.GetBallisticCoefficient()` throws
`ArgumentException: If form-factor is used, the bullet diameter must be set` — a form factor is turned
into a coefficient through the bullet's sectional density, which needs the diameter.

**Verified** by calling `ShotTrajectoryCalculator.Calculate` with exactly that data in a throwaway test:
the exception is real and comes out of the calculation, not out of validation.

**Why it matters more than it looks:** this is not an exotic combination. **Every `.drg` shot is a
form-factor shot** — `Browse…` sets the BC to `1 GC` and ticks the switch — so any custom drag table
whose header carries no diameter lands here. `Browse…` fills the diameter when the file has one, and
older `.drg` files store that slot as `0`.

**Where it goes wrong architecturally:** nothing on the path catches it. `OpenNewTrajectory` is
`async void`, so the exception surfaces as an unhandled exception on the UI thread rather than as a
message the user can act on. `ShotDataPanel.Validate` checks that fields are *present*, not that the
combination is *computable*.

**Suggested fix:** validate the combination where the other validation lives — if the form-factor switch
is on, require a diameter, and say so in the same style as the existing messages. A `try`/`catch` around
the calculation with the exception text shown would also be an improvement over a crash, but it treats
the symptom.

### F-1b — same class: a GC coefficient whose `.drg` cannot be found

`ValidateDragTable` throws `ArgumentNullException("The drag table shoudn't be null if the ballistic
coefficient is custom")` when the BC table is `GC` and no table was supplied. That happens when
`CustomDragTableLoader.ResolvePath` cannot find the stored file name — neither as given nor under
`data/drg` and its subfolders. Realistic route: someone opens a shared `.trajectory` or `.ammox` that
references a `.drg` they do not have. Same uncaught path, same `async void`.

### F-1c — same class: a zero distance the bullet cannot reach

`CalculateZeroParameters` throws `InvalidOperationException("The projectile cannot reach the zero
distance")`. Found while writing `docs/zero-tab.md`; reachable by asking for a zero further out than the
load can carry (a subsonic pistol load zeroed at 1,000). Again nothing catches it.

**Taken together**, F-1/1b/1c say the same thing: the calculation raises meaningful exceptions and the
UI has no seam for turning them into messages. One `try`/`catch` at the call sites plus a dialog would
cover all three, and the specific validations are then a refinement rather than a necessity.

## F-2 — Nothing catches a calculation failure on the recalculate path either

- **Found:** 2026-07-28
- **Status:** open (same root as F-1, listed separately because it is a second call site)
- **Area:** `MainWindow` — `View → Edit Parameters` recalculates through
  `ShotCalculator.Calculate(dialog.Result, …)` with no `try`

The same three exceptions can be raised by editing an existing shot into an uncomputable state, which is
arguably the likelier route: the window already exists, so a crash there loses work the user can see.
`DoSave` and `Open` do wrap their I/O in `try`/`catch` (writing to `Console.Error`), so the pattern
exists in the file — it is the calculation that is unguarded.

## F-3 — `AmmoPanel` does not restate units after a load, so the tab can show two systems at once

- **Found:** 2026-07-28, writing `docs/ammunition-tab.md`
- **Status:** open
- **Area:** `Common/BallisticCalculator.Panels/Panels/AmmoPanel.axaml.cs` — the `Ammunition` setter

**Steps to reproduce**

1. `Trajectory → New → Imperial`.
2. On the Ammunition tab press **Load** and pick `data/legacy-ammo/7N6.ammo`.
3. Look at the tab: weight in **grams**, muzzle velocity in **m/s**, diameter and length in **mm**,
   everything else on the dialog in imperial.

The shipped library contains both kinds, which is what makes this easy to hit: `7N6.ammo` is stored
metric (`3.4g`, `870m/s`, `5.6mm`), `45acp 230gr FMJ (4in).ammo` imperial (`230gr`, `850ft/s`, `0.451in`).

**Why it happens:** the setter uses `SetValue`, which preserves each value's own unit by design — the
precision-transparency rule in `CLAUDE.md`. That is correct for *precision* and wrong for *presentation*,
and it is precisely the defect that was fixed for `AtmospherePanel` on 2026-07-27 (commit `3c49dbc`),
where the setter now ends with `ApplyMeasurementSystem(convert: true)`.

**Rule it breaks:** [`units.md`](units.md) rule 1 — "a dialog is either imperial or metric, never both.
No field opts out." `units.md` also flags this as the decision to watch.

**Suggested fix:** the `AtmospherePanel` fix, applied here — restate every field in the panel's system at
the end of the setter, converting rather than relabelling. Worth checking the other panels that take a
library object with its own units in the same pass: `ZeroAmmoPanel` (wraps `AmmoPanel`), `RiflePanel`
(sight height and twist from a preset or a file), `WindPanel`, `ParametersPanel`.

**Note for the manual:** `docs/ammunition-tab.md` currently documents the behaviour as it is ("a loaded
value keeps the units it was saved in"), with the shipped files as the example. Fixing this makes one
paragraph there wrong — search for *"A loaded value keeps the units"*.

## F-4 — A ticked but half-filled zero override is silently ignored

- **Found:** 2026-07-28, writing `docs/zero-tab.md`
- **Status:** open
- **Area:** `ZeroAmmoPanel.Ammunition`, `ZeroAtmospherePanel.Atmosphere` (and `ZeroWindPanel.Wind` by the
  same shape), plus `ShotDataPanel.Validate`, which never looks at them

Each override getter returns null when its checkbox is clear — correct — but also when the checkbox is
**ticked and the fields are incomplete**, because it just forwards the inner panel's own null. Null then
means "same as the shot" in `ZeroingCalculator.BuildInputs`
(`ZeroAmmunition = zeroParams.Ammunition ?? ammo`), so:

> Tick **Other ammunition for zero**, fill in a BC and a muzzle velocity but forget the weight, press OK
> — the shot computes, with the zero silently using the *shot's* ammunition. Nothing says so.

This is the same failure mode the dialog is careful about everywhere else: `Validate` reports a
half-filled Weather or Rifle tab as *"Not all required data filled in"*. The zero overrides are outside
that check, and they are the one place where the fallback is plausible enough to go unnoticed — the
numbers move a little, not obviously.

**Suggested fix:** have `ZeroPanel` report "ticked but incomplete" for each group, and add it to
`Validate`'s `incompletePanels` as `Zero`. Cheap, and it closes the last silent path in that dialog.

**Documented meanwhile:** `docs/zero-tab.md` states it as a trap under "Things that catch people out".
